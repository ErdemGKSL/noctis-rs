## 1. Mental model: recoverable vs. bugs

Rust splits failure into two kinds, and choosing the right one is the whole game:

| Situation | Mechanism | Example |
| --- | --- | --- |
| Something outside the program went wrong (input, I/O, network, config, user) | `Result<T, E>` | file missing, JSON malformed, HTTP 503 |
| The program itself is wrong (a broken invariant, a bug) | `panic!` (via `unwrap`, `expect`, `assert!`, indexing) | index computed out of bounds, "unreachable" state reached |

**Why:** a `Result` is part of the function's contract — the caller is forced to decide what
to do. A panic says "continuing would be meaningless". Panicking on bad input turns a
user mistake into a crash; returning `Result` for a bug hides the bug behind error-handling
noise.

Rule of thumb: if a *correct* program can still hit the failure, it's a `Result`.

## 2. `Result` and `?` everywhere

`?` returns early on `Err` and converts the error with `From::from`. That conversion is what
makes layered errors cheap to write.

```rust
// ❌ manual matching — noisy and easy to get wrong
fn read_port(path: &str) -> Result<u16, ConfigError> {
    let text = match std::fs::read_to_string(path) {
        Ok(t) => t,
        Err(e) => return Err(ConfigError::Io(e)),
    };
    match text.trim().parse::<u16>() {
        Ok(p) => Ok(p),
        Err(e) => Err(ConfigError::Parse(e)),
    }
}
```

```rust
// ✅ `?` + `From` impls (generated by thiserror's #[from])
use std::num::ParseIntError;

#[derive(Debug, thiserror::Error)]
pub enum ConfigError {
    #[error("could not read config")]
    Io(#[from] std::io::Error),
    #[error("port is not a number")]
    Parse(#[from] ParseIntError),
}

pub fn read_port(path: &str) -> Result<u16, ConfigError> {
    let text = std::fs::read_to_string(path)?;
    Ok(text.trim().parse()?)
}
```

Notes:

- `?` also works on `Option` inside functions returning `Option`.
- `?` in closures needs the closure to return `Result`/`Option`; for iterators collect into
  `Result<Vec<_>, _>` (see §7).
- Type aliases keep signatures short: `pub type Result<T, E = Error> = std::result::Result<T, E>;`
  — define it per crate/module, default the error param so `Result<T, Other>` still works.

## 3. Library errors: typed enums with `thiserror`

Libraries should return a concrete error type the caller can `match` on. `thiserror`
generates `Display`, `std::error::Error` (including `source()`), and `From` impls with zero
runtime cost and nothing leaking into your public API.

```rust
use std::path::PathBuf;

#[derive(Debug, thiserror::Error)]
#[non_exhaustive] // lets you add variants without a breaking change
pub enum StoreError {
    /// Wraps the cause; `source()` returns it, Display does not repeat it.
    #[error("failed to open store at {path}")]
    Open {
        path: PathBuf,
        #[source]
        source: std::io::Error,
    },

    /// `#[from]` implies `#[source]` and generates `From<serde_json::Error>`.
    #[error("store file is corrupted")]
    Corrupt(#[from] serde_json::Error),

    /// Pure domain error, no underlying cause.
    #[error("key `{0}` not found")]
    NotFound(String),

    /// Forward Display and source() to the inner error entirely.
    #[error(transparent)]
    Other(#[from] OtherLibError),
}
#[derive(Debug, thiserror::Error)] #[error("other")] pub struct OtherLibError;
```

Guidelines:

- **Display messages:** lowercase, no trailing period, describe *this* layer only. Don't
  embed `{source}` in the message when you also expose it via `#[source]` — reporters walk
  the chain and you'd print it twice.
- **Add context fields** (`path`, `key`, `id`) to variants; a bare `Io(io::Error)` says
  "file not found" but not *which* file.
- **`#[from]` only when the mapping is unambiguous.** If two different operations can
  produce `io::Error` and you want to tell them apart, use explicit `map_err` into
  different variants instead of one `#[from]`.
- **Don't expose `Box<dyn Error>` or `anyhow::Error` in a library API** — callers can't
  match on it, and it forces your dependency choices on them.
- **Mark public error enums `#[non_exhaustive]`** unless the set is truly closed.
- Errors should be `Send + Sync + 'static` so they cross threads and fit into `anyhow`.

Hand-rolled equivalent (useful if you avoid the dependency) — implement `Debug`, `Display`,
`Error::source`, and the `From` impls manually. `thiserror` exists precisely so you don't.

## 4. Error granularity: one enum per module or operation

A single crate-wide `Error` with 40 variants makes every function look like it can fail in
40 ways. Prefer an error type per module or per meaningful operation, and compose them.

```rust
#[derive(Debug, thiserror::Error)]
pub enum ParseError {
    #[error("unexpected end of input")]
    Eof,
    #[error("invalid token at byte {0}")]
    InvalidToken(usize),
}

#[derive(Debug, thiserror::Error)]
pub enum LoadError {
    #[error("could not read file")]
    Io(#[from] std::io::Error),
    #[error("could not parse file")]
    Parse(#[from] ParseError),
}
```

**Why:** the signature `fn parse(..) -> Result<_, ParseError>` documents exactly what can go
wrong; callers handling `Eof` don't have to wade through network errors.

Balance: don't go to the other extreme of one enum per function in a tiny crate. "One per
module or per public operation family" is the usual sweet spot.

## 5. Application errors: `anyhow` with context

Binaries mostly *report* errors rather than match on them. `anyhow::Error` (or
`eyre::Report` / `color-eyre` for prettier output) erases the type and lets you attach a
chain of human-readable context.

```rust
use anyhow::{Context, Result, bail, ensure};

fn load_settings(path: &std::path::Path) -> Result<Settings> {
    let text = std::fs::read_to_string(path)
        .with_context(|| format!("reading settings from {}", path.display()))?;
    let settings: Settings = toml::from_str(&text).context("parsing settings TOML")?;
    ensure!(settings.workers > 0, "workers must be at least 1");
    if settings.name.is_empty() {
        bail!("settings.name must not be empty");
    }
    Ok(settings)
}
#[derive(serde::Deserialize)] struct Settings { workers: u32, name: String }
```

- `.context("static str")` for cheap constant messages; `.with_context(|| format!(..))`
  when the message allocates — the closure only runs on the error path.
- Context describes **what you were trying to do**, not what went wrong (the source already
  says that): `"reading settings from cfg.toml"` → `"No such file or directory"`.
- Printing with `{:#}` gives the one-line chain; `{:?}` gives the multi-line chain with
  backtrace (when `RUST_BACKTRACE=1`).
- Need to react to a specific cause? `err.downcast_ref::<StoreError>()`. If you do this a
  lot, that layer wants a typed error instead.

Mixed approach that scales: typed `thiserror` errors in library-like modules/crates,
`anyhow` in `main.rs`, command handlers and glue code.

## 6. `unwrap` / `expect` policy

| Where | Policy |
| --- | --- |
| Tests, examples, prototypes | `unwrap()` is fine — a panic is a test failure |
| Production, value derived from input/I/O/env | never panic; use `?` |
| Production, invariant you have *proven* | `expect("…why this cannot fail…")` |
| Constants known at compile time | prefer compile-time construction; otherwise `expect` |

Write `expect` messages as the **invariant that should hold**, not as an error message —
when it fires, the reader learns which assumption broke:

```rust
// ❌ restates the failure, says nothing about why it should not happen
let re = regex::Regex::new(r"^\d+$").expect("regex failed");

// ✅ states the invariant
let re = regex::Regex::new(r"^\d+$").expect("hard-coded regex is valid");
```

Better still, remove the failure path entirely: `LazyLock<Regex>`, `NonZeroU32::new(..)`
in a `const`, `let Some(x) = .. else { unreachable!(..) }` with an explanation, or a type
that makes the bad case impossible.

Other panic sources to be deliberate about: slice indexing `v[i]` (use `.get(i)` on
untrusted indices), integer overflow in release (wraps silently — use `checked_*`,
`saturating_*`, or `wrapping_*` to state intent), `RefCell::borrow_mut`, `Mutex::lock().unwrap()`
(acceptable: poisoning means another thread already panicked).

Clippy can enforce this: `#![warn(clippy::unwrap_used, clippy::expect_used)]` in library
crates, with `#[cfg(test)]` modules allowed via `allow-unwrap-in-tests = true` in `clippy.toml`.

## 7. `Option` ↔ `Result` combinators

```rust
fn find_user<'a>(users: &'a [User], name: &str) -> Result<&'a User, LookupError> {
    users
        .iter()
        .find(|u| u.name == name)
        // ok_or_else: the error is built only on the None path
        .ok_or_else(|| LookupError::UnknownUser(name.to_owned()))
}
struct User { name: String }
#[derive(Debug)] enum LookupError { UnknownUser(String) }
```

- `ok_or(e)` evaluates `e` eagerly — fine for unit-like variants, use `ok_or_else` when it
  allocates or formats.
- `map_err` to translate errors at module boundaries; `.ok()` to *intentionally* drop an
  error (say why in a comment if it isn't obvious).
- `transpose()` swaps `Option<Result<T,E>>` ↔ `Result<Option<T>,E>` — handy with optional
  fields that need parsing.
- Collecting: `iter.map(parse).collect::<Result<Vec<_>, _>>()` stops at the first error. To
  keep all errors, `partition` into oks and errs.
- `let ... else` keeps the happy path unindented:

```rust
fn port_of(url: &str) -> Result<u16, String> {
    let Some((_, rest)) = url.split_once("://") else {
        return Err(format!("missing scheme in `{url}`"));
    };
    let Some((_, port)) = rest.split_once(':') else {
        return Ok(80); // no explicit port
    };
    port.trim_end_matches('/').parse().map_err(|e| format!("bad port: {e}"))
}
```

## 8. `main`, exit codes and reporting

```rust
// Simple apps: errors are printed with Debug formatting and exit code 1.
fn main() -> anyhow::Result<()> {
    run()
}
fn run() -> anyhow::Result<()> { Ok(()) }
```

When you need control over formatting or distinct exit codes, return `ExitCode`:

```rust
use std::process::ExitCode;

fn main() -> ExitCode {
    match run() {
        Ok(()) => ExitCode::SUCCESS,
        Err(err) => {
            eprintln!("error: {err:#}"); // one-line chain: "reading config: No such file"
            ExitCode::from(2)
        }
    }
}
fn run() -> anyhow::Result<()> { Ok(()) }
```

Avoid `std::process::exit` deep inside the program: it skips destructors (flushing
buffers, temp-file cleanup). Bubble errors up to `main` instead.

## 9. Log once, at the edge

```rust
// ❌ logs and returns — the same failure ends up in the logs 3 times, at 3 layers
fn save(&self) -> Result<(), StoreError> {
    self.write().map_err(|e| {
        tracing::error!("write failed: {e}");
        e
    })
}
```

Either **handle** an error (log it, retry, fall back, convert to a response) **or propagate**
it with added context — not both. The top level (request handler, `main`, task supervisor)
logs it once with the full chain. In `tracing`, record errors as fields:
`tracing::error!(error = %err, "request failed")` or `error = ?err` for the debug chain.

## 10. `#[must_use]` and ignored results

`Result` is already `#[must_use]`, so `fallible();` warns. Don't silence it with `let _ =`
unless ignoring is genuinely correct — and then say why:

```rust
// Receiver may have hung up during shutdown; nothing left to notify.
let _ = shutdown_tx.send(());
```

Mark your own types/functions `#[must_use]` when dropping the value is almost always a bug
(builders, guards, pure functions returning a new value):
`#[must_use = "the new config is returned, the original is unchanged"]`.

## 11. Pitfalls checklist

- **Stringly errors** — `Result<T, String>` or `Err("bad".into())` can't be matched,
  carries no source chain, and invites typos. Use an enum (lib) or `anyhow!` (app).
- **Swallowing errors** — `if let Ok(x) = f() { .. }` silently ignores failures; `.ok()`
  and `unwrap_or_default()` too. Make sure that's intended.
- **Losing the source** — `map_err(|_| MyError::Failed)` throws the cause away. Keep it
  with `#[source]`, or `map_err(|e| MyError::Failed(e))`.
- **Duplicated messages** — `#[error("io error: {0}")]` with `#[from]` prints the inner
  message twice when a reporter walks the chain.
- **Panicking in `Drop`** or in code called from `Drop` — a panic during unwinding aborts.
- **`Box<dyn Error>` without `Send + Sync`** — it won't cross `tokio::spawn` boundaries;
  write `Box<dyn Error + Send + Sync>` if you must box.
- **Catching panics as control flow** (`catch_unwind`) — only for FFI boundaries and
  thread/task isolation, never as an exception mechanism.
