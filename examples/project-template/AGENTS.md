## noctis-bot-template

A Discord bot built on Noctis (Rust, tokio, twilight). It is a copy of the Noctis
project template: `/setup start` (Wizard), `/dashboard` (Navbar + Paginator),
`/profile` and "Show profile" (rendered card in a Media Gallery, bio modal), a custom
`CacheStore` Adapter and `en-US`/`tr` Locale files.

## Policy

- Learn Noctis **only** from `.claude/skills/noctis/` (the Noctis Usage Skill). Load it before writing or reviewing any bot code: commands, Routes, Views, modals, Templates, Adapters, i18n, tests.
- Never read Noctis source: not `../../crates/noctis*`, not `~/.cargo/registry/**/noctis*`, not `~/.cargo/git/**/noctis*`, not docs.rs source views, not `target/` expansions. If the skill does not cover something, say so and stop on that point; do not guess and do not open the source.
- For general Rust (types, errors, async, tests, crate layout), use the `rust-best-practices` skill and read only the `references/*.md` files the task touches.
- Follow the UI Doctrine in the skill (UD-1..UD-8): Components V2 Views for anything interactive, images only for read-only visuals, option-light commands that open Views, no per-message listeners or collectors.

## Where things are

- `src/bootstrap.rs` first run: loads `.env`, or creates it from the embedded `.env.example` with a fresh payload key.
- `src/main.rs` thin entry; `src/lib.rs` `configure(&mut AppBuilder) -> &mut AppBuilder` mounts Modules, Adapters and state (shared by main and tests).
- `src/observability.rs` the `AlertSink` Error Sink for the `Event` and `Render` origins.
- `src/modules/{setup,dashboard,profile}.rs` one Module each; `src/adapters/` custom Adapters; `src/strings.rs` compiles `locales/*.yaml` (`en-US` is the default locale; file names are Discord locale codes).
- `noctis-theme.css` Theme tokens and keyframes for Templates.
- `tests/` flows (testkit), Adapter conformance, Template pixel snapshots.

## Running and verifying

- Before calling Rust work done, run `cargo fmt`, `cargo clippy --release --all-targets -- -D warnings` and `cargo test --release`.
- Always build, test, check and run with `--release`; never create a debug build (disk space in cloud sessions is limited). If the disk fills anyway, delete `target/debug/`.
- Run locally with `NOCTIS_TOKEN` set: `cargo run --release -- --publish-guild <test guild id>` once, then `cargo run --release`. See `README.md`.
- Compile errors and `BuildError`s name a Discord rule id such as `[CID-01]` or `[CMD-11]`. Look the id up in `.claude/skills/noctis/references/limits-cheatsheet.md` (and `troubleshooting.md`); fix the cause the error's `help:` line names instead of working around the check.

## Conventions that differ from defaults

- Ship one self-contained binary: compile every asset in (`i18n!` for locales, `theme!()` for the theme, `include_bytes!`/`include_str!` for fonts, images and `.env.example`); never read asset files at runtime, only `.env`. Embedded data used once (like `.env.example`) is never copied to the heap; any buffer built from it, and every secret, lives in `zeroize::Zeroizing`. Data used on every interaction (locales) stays resident.
- Never hand-build a `custom_id`, response type or interaction callback; build components from Route values and return Views.
- Every user-visible string goes through `locales/*.yaml`; add new keys to `en-US.yaml` first.
- Limits and Locales come from `noctis::rules` (`Locale::EnUs` = `en-US`); override limits on the App builder with `Limits`, never with hard-coded numbers.
- Slash Commands are `#[command("path or pattern", description = "…")]` on an `async fn(ctx: CommandCtx) -> HandlerResult<R>` that answers: `R` is a `V2Message`/`Components` (a `LegacyMessage` only for plain notices), or the `Responded` from the Responder (`HandlerResult<()>` does not compile); the description is a literal equal to `cmd.<path>.description` in `locales/en-US.yaml` (doc comments are rustdoc only). A pattern with a group (`"config (set|get) (prefix|welcome)"`) generates `enum <Fn>Path` (here `ConfigPath`), which the handler takes as its second parameter and `match`es; resolve a variant collision by renaming an alternative, and raise the 25-expansion cap only with `max_expansions = n`. See `references/commands.md` §1-2.
- Command options are one `#[derive(Options)]` struct taken as the handler's last parameter. Every field has `#[option(description = "…")]`, a literal equal to `cmd.<path>.opt.<name>.description` in `locales/en-US.yaml`; `Option<T>` fields (optional) come after required ones; bounds use `min_value`/`max_value`/`min_length`/`max_length`; validators are `fn(&T, &CommandCtx) -> Result<(), MessageKey>`; choices come from a `#[derive(Choices)]` enum. Decode errors are typed (`OptionError`, `InvalidOption`), never unwrapped. See `references/commands.md` §3.
- Command metadata goes in the attribute: `permissions = MANAGE_GUILD | BAN_MEMBERS` (twilight `Permissions` names, `ADMINISTRATOR` for admin-only), `contexts = [Guild]`, `integration_types = [GuildInstall]`, `nsfw = true`, and `guilds = [<id literal>]` for a guild-scoped command (which then takes no `contexts`/`integration_types`, META-03); unset means omitted, and the values belong to the base command (META-02). Context menus are `#[user_command("Show profile")]` / `#[message_command("Quote")]` on `async fn(ctx: CommandCtx, target: ResolvedUser | ResolvedMessage[, r: CommandResponder]) -> HandlerResult<R>` (answering like a slash Command): names 1-32 characters (CTX-01), no description or options (CTX-02), same metadata arguments; a missing target is a typed `MenuTargetError`. See `references/commands.md` §1 and §5.
- Answer a Command by returning its message (sent as the reply, or as an edit of the original after a `defer`/`reply`); take `r: CommandResponder` (after `ctx` and the path, before the options) only for follow-ups, deferring slow work (`r.defer(Ephemerality::…)` before ~2.9 s) or several messages, and end with `Ok(acked.done())`. Declare private Commands with the bare `ephemeral` flag, never per call; `followup(msg, Visibility::…)` picks each follow-up's visibility, and no edit changes it. Handle every `ResponderError` with `?`; failures reach the `Command` Error Sink. Run a Command from an event handler (prefix commands) only through `ctx.dispatcher().run_command(CommandInvocation::new(..))`, which replies to the message and cannot be ephemeral. See `references/responder.md` §1-4.
- Commands of every Module merge per scope at `App::build` (one base word = one Discord command). Declare each base and group description (and shared base metadata) once with `Module::base(name, BaseMeta::new().description(..))` / `Module::group(path, description)`, equal to `cmd.<path>.description`; leaves under one base must agree on metadata or the base declares it. Fix a `BuildViolation::Command` by its rule id and the Modules its notes name; never rely on the description fallback (it logs a `noctis::registry` warning). See `references/commands.md` §1 and §6.
- Dynamically built Command Patterns are checked with `noctis::rules::command::{validate_pattern_spacing, expand, validate_tree}` before registering; never hand-split patterns. Dynamically declared options go through `noctis::rules::command::validate_options` and `measure_options` (as `with_options(opts.len(), measure_options(&opts, &limits))`) before registering.
- Dynamic component trees, modals, attachments and webhook names can be pre-checked with `noctis::rules::{component, modal, attachment, message}` (`validate_components`, `validate_modal`, `validate_attachments`, `validate_webhook_name`, …), whole messages and runtime-built `noctis::ui::Modal`s with `noctis::ui::validate(&mut msg, &limits)` / `noctis::ui::cost(&msg, &limits)` (`validate` also takes a `Modal`), and autocomplete responses with `noctis::rules::command::validate_autocomplete`; never hard-code their limits. Write fixed-shape trees with `noctis::components!`, literals with `label!`/`placeholder!`/`content!`/`rgb!`, and modal forms with `#[derive(Modal)]` plus `#[derive(Choices)]` option sets (all checked at `cargo check`); decode modal submissions with `ModalForm::from_json` and handle every `SubmitError` (never unwrap untrusted input).
- Custom Payload field types implement `noctis::codec::{Field, FieldDecode}` and are tested with `noctis::codec::check::{assert_round_trip, assert_worst_case}` (see `references/routes-payloads-refs.md` §2); never hand-escape field text. Only `Option` fields may be appended to a Payload without a schema bump, since missing trailing fields decode as `None` through `FieldDecode::absent`; never override `absent` on your own types.
- Routes are `#[derive(Route)]` structs with one `#[route("id", args…)]`; the codec arguments are `by_ref`, `overflow = spill`, `schema = n`, `view`, `select` and `signed` (runtime arguments such as `owner`, `permissions`, `opens_modal`, `ttl` are [planned] and rejected until their release). The derive proves at compile time that every `custom_id` fits 100 characters (`[CID-01]`); keep each Route's width line (from `cargo test --release -- --nocapture noctis_route_width`) in its doc comment. Small closed sets are `#[derive(PayloadEnum)]` unit enums (one character, at most 62 variants; append variants, never reorder or remove them without bumping `schema`). `#[derive(Payload)]` is only for the Payload of a hand-written `Route`.
- Gateway events are `#[event]` handlers (`async fn(ctx: EventCtx, event: <noctis::events payload>) -> HandlerResult<()>`) added to a Module and mounted with `AppBuilder::module`; see `references/modules-middleware-ratelimits.md` §4. Their intents are derived: never request a non-privileged intent just for a handler, request privileged ones (`GUILD_MEMBERS`, `GUILD_PRESENCES`, `MESSAGE_CONTENT`) with `.intents(..)`, and fix a `[GW-05]` `BuildError` by requesting the intent it names and enabling it in the Developer Portal. Keep handlers idempotent; mark `ordered` only when per-guild order matters.
- Handler failures go to Error Sinks: route an origin with `.error_sink(ErrorOrigin::…, sink)` (see `src/observability.rs` and `references/modules-middleware-ratelimits.md` §6); a sink is synchronous and must not block, so forward to a channel for I/O. noctis emits only the metrics listed in `noctis::observe::METRICS` (`references/app-and-sharding.md` §11); install your own `tracing` subscriber and `metrics` recorder, and never put ids or free text in metric labels.
- Shutdown is graceful: `app.run()` stops on Ctrl-C/SIGTERM and gives queued events and running handlers `.shutdown_grace(..)` (default 10 s, `NOCTIS_SHUTDOWN_GRACE`) before cancelling them (`ReportKind::Cancelled`); keep handlers cancel-safe at every `.await`, never block a thread inside one, and use `app.run_until(fut)` in tests instead of signals. A `RunError::AllShardsEnded` from `run` means every shard closed fatally: read the `shard closed fatally` logs (see `references/app-and-sharding.md` §8).
- Discord HTTP goes through the App's one client (`ctx.http()`), which a built-in edge keeps warm with HTTP/2 PINGs and redials when it dies; never poll an endpoint (such as `GET /users/@me`) to keep HTTP warm, and tune only through `.http(HttpConfig)` (`references/app-and-sharding.md` §5). An interaction must be acknowledged within 2.9 s of receipt (`AckDeadlineMissed`): defer before slow work.
- Storage goes through ports (`noctis::ports`), never a `static` map: the bounded defaults live in `noctis::ports::memory` (`MemoryCacheStore`, `MemoryDiscordCache`, `MemoryIdentifyQueue`, …; see `references/adapters.md` §1.1), and a custom Adapter implements the port trait the way `src/adapters/bounded_cache.rs` does (verbatim keys, opaque `Bytes`, atomic ops, bounded).
- Inside the noctis-rs monorepo this crate is standalone (`[workspace]` in its `Cargo.toml`); the monorepo root `Cargo.toml` must keep `exclude = ["examples/project-template"]`. After copying it out, switch the `noctis` dependency to the crates.io form shown in `Cargo.toml`.
