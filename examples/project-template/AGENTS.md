## noctis-bot-template

A Discord bot built on Noctis (Rust, tokio, twilight). It is a copy of the Noctis
project template: `/setup start` (hand-written step flow), `/dashboard` (hand-written
tabs and pagination, module toggles), `/profile` and "Show profile" (rendered card in a
Media Gallery, bio modal), a custom
`CacheStore` Adapter and `en-US`/`tr` Locale files.

## Policy

- Learn Noctis **only** from `.claude/skills/noctis/` (the Noctis Usage Skill). Load it before writing or reviewing any bot code: commands, Routes, Views, modals, Templates, Adapters, i18n, tests.
- Never read Noctis source: not `../../crates/noctis*`, not `~/.cargo/registry/**/noctis*`, not `~/.cargo/git/**/noctis*`, not docs.rs source views, not `target/` expansions. If the skill does not cover something, say so and stop on that point; do not guess and do not open the source.
- For general Rust (types, errors, async, tests, crate layout), use the `rust-best-practices` skill and read only the `references/*.md` files the task touches.
- Follow the UI Doctrine in the skill (UD-1..UD-8): Components V2 Views for anything interactive, images only for read-only visuals, option-light commands that open Views, no per-message listeners or collectors. Noctis has no UI widgets: write tabs, pagination and step flows by hand from the recipes in `references/views-and-recipes.md`. Size a page with `noctis::ui::Budget::of(&fixed_parts, ctx.limits()).fits(&worst_case_row)` (fixed parts measured with their variable text at its longest), never with hard-coded row counts; see the dashboard's Roles tab. Select handlers read the pick with `ctx.values()` (a `SelectedValues`: `strings()`, `users()`, `roles()`, `channels()`), and the recipes in `references/views-and-recipes.md` §3 are verbatim copies of noctis-rs's tested `examples/ui-recipes/`.

## Where things are

- `src/bootstrap.rs` first run: loads `.env`, or creates it from the embedded `.env.example` with a fresh payload key.
- `src/main.rs` thin entry; `src/lib.rs` `configure(&mut AppBuilder) -> &mut AppBuilder` mounts Modules, Adapters and state (shared by main and tests).
- `src/observability.rs` the `AlertSink` Error Sink for the `Event` and `Render` origins.
- `src/modules/{setup,dashboard,profile}/` one Module each: `mod.rs` (Module and component structs), `view.rs` (render functions), `handlers.rs` (Command structs and every `#[handler]` impl), `events.rs` (gateway events); `src/adapters/` custom Adapters; `src/strings.rs` compiles `locales/*.yaml` (`en-US` is the default locale; file names are Discord locale codes).
- `noctis-theme.css` Theme tokens and keyframes for Templates.
- `tests/` flows (`noctis::testkit::TestApp`, `#[tokio::test(flavor = "multi_thread")]`), `memory.rs` (`assert_memory_flat`, its own binary with the dhat allocator and one `#[test]`), Adapter conformance, Template pixel snapshots.

## Running and verifying

- Before calling Rust work done, run `cargo fmt`, `cargo clippy --release --all-targets -- -D warnings` and `cargo test --release`.
- Always build, test, check and run with `--release`; never create a debug build (disk space in cloud sessions is limited). If the disk fills anyway, delete `target/debug/`.
- Run locally with `NOCTIS_TOKEN` set: `cargo run --release -- --publish-guild <test guild id>` once, then `cargo run --release`; add `--no-resume` for a full reset that starts and stops with fresh sessions (no RESUME). See `README.md`.
- Commands reach Discord only through Publish (`--publish-guild [<id>]` in dev, `--publish` or one `NOCTIS_PUBLISHER=true` process in prod; add `--dry-run` to preview); never publish on READY. Tests start Apps with `app.run_with_args(std::iter::empty::<&str>())`, never `app.run()`, which rejects the test harness's flags.
- Compile errors and `BuildError`s name a Discord rule id such as `[CID-01]` or `[CMD-11]`. Look the id up in `.claude/skills/noctis/references/limits-cheatsheet.md` (and `troubleshooting.md`); fix the cause the error's `help:` line names instead of working around the check.

## Conventions that differ from defaults

- Ship one self-contained binary: compile every asset in (`i18n!` for locales, `theme!()` for the theme, `include_bytes!`/`include_str!` for fonts, images and `.env.example`); never read asset files at runtime, only `.env`. Embedded data used once (like `.env.example`) is never copied to the heap; any buffer built from it, and every secret, lives in `zeroize::Zeroizing`. Data used on every interaction (locales) stays resident.
- Never hand-build a `custom_id`, response type or interaction callback; build components from their struct values with `.build()`.
- A View is a plain function: write one `render_x(data, &strings, ids…) -> V2Message` per screen in the feature's `view.rs`, keep it pure (load data in the handler first), and call it from the Command and from every component and modal handler. Every handler goes: decode the Payload (`self` in the `#[handler]` method) → validate/authorize → write storage → answer with one call: `ctx.respond(render_x(..))` from a Command (a new message; after the auto-defer it edits the loading message, once answered it follows up), `ctx.update(render_x(..))` from a component or modal handler (it updates the clicked message in place; never on `CommandCtx`, and a modal opened from a slash command has no message, so `ctx.update` is `UpdateUnavailable` there and you answer with `ctx.respond`), and `ctx.reply_text(key)` for a one-line ephemeral notice (`.public()` for everyone). Each returns `HandlerResult<Responded>`; return it. A second initial response in the same handler is `ResponderError::AlreadyResponded`. Returning the message (`HandlerResult<V2Message>`) still works and sends the same thing. UI state (selected entity, tab, page, step) lives only in typed Payload fields of the feature's own Routes; never store it per message.
- Pass user text (names, reasons, bios) through `escape_markdown` (and `escape_mentions` where mentions must not render) before putting it in a Text Display; every select gets a fresh nonce per send, so always set its defaults to the current value.
- Every user-visible string goes through `locales/*.yaml` (`src/strings.rs`'s `i18n!`): add new keys to `en-US.yaml` first, then to `tr.yaml` with the same placeholders; a key `tr.yaml` lacks is a `[LOC-04]` build warning (it falls back to English), a key `en-US.yaml` lacks or a wrong argument does not compile. Keep this one App-level catalog (`.locales(strings::catalog())`); use `Module::new(..).locales(its_strings::catalog())` only for a Module shipped as its own crate or with its own `i18n!` `dir` (its keys still resolve App-wide, and a key two catalogs define fails `build()` with a `DuplicateLocaleKey` naming both catalogs and their owners (a Module or `AppBuilder::locales`)). See `references/i18n.md`.
- Runtime locale overlays (translator fixes without a redeploy) come only through a `LocaleSource` Adapter (`.locale_source(..)`): it is loaded once at startup per locale with a file, may overlay content keys only, never `cmd.*`/`cmdword.*`/`ctxcmd.*`/`noctis.*`, with the compiled placeholders; a failed load or any rejected pair stops `run` with `Error::LocaleOverlay` (`LocaleOverlayError::Load`/`Invalid`), so fix the data, not the code. Restart to pick up edits. See `references/i18n.md` §8.
- Limits and Locales come from `noctis::rules` (`Locale::EnUs` = `en-US`); override limits on the App builder with `Limits`, never with hard-coded numbers.
- Pick the locale by audience: `ctx.user_locale()` for ephemeral, single-user UI, `ctx.guild_locale()` for shared content, `ctx.response_locale()` when it follows the reply's visibility. All three return a resolved `Locale`: the built-in resolution picks a locale with a file (a sibling such as `en-GB` → `en-US`, then the App default), while an override is used verbatim; a per-guild override goes in `AppBuilder::locale_resolver(..)` or a before-Middleware's `ctx.set_guild_locale(..)`. Either way `Strings::of(..)` renders through the catalog's own fallback, so no manual fallback is needed. See `references/i18n.md` §7.
- One struct per interaction, one style only: the derive names the kind and the struct holds the id and the typed data; its handler is always `impl X { #[handler] async fn handle(self, ctx: …) -> HandlerResult<R> }` (`#[handler]` takes no arguments; free-function handlers do not exist), and the Module registers it by type, `Module::new("x").add::<X>()`. Slash Commands are `#[derive(SlashCommand)]` structs with `#[command("path or pattern")]` (a unit struct when there are no options) whose handler answers: `R` is a `V2Message`/`Components` (a `LegacyMessage` only for plain notices), or the `Responded` from the Responder (`HandlerResult<()>` does not compile). `locales/*.yaml` is the source of every command text: the macro reads the description from `cmd.<path>.description` in `locales/en-US.yaml` (a missing key is a `[CMD-04]` compile error; never add a `description = "…"` literal, doc comments are rustdoc only), and Publish sends each file's `cmd.<path>.name|description` (or `cmdword.<word>`) as Discord's name/description localizations, checked at `cargo check` and `App::build` (`[LOC-02]`/`[LOC-03]`, `BuildViolation::CommandLocalization`). Dispatch always routes on the default (English) names. A pattern with a group (`"config (set|get) (prefix|welcome)"`) generates `enum <Struct>Path` (here `ConfigPath` for `struct Config`), which the handler takes after `ctx` and `match`es; resolve a variant collision by renaming an alternative, and raise the 25-expansion cap only with `max_expansions = n`. Any handler (Command, context menu, component, modal, event) may also take `Ext<T>` / `Option<Ext<T>>` parameters anywhere after `ctx` and before the responder, filled by its Module's Middleware. See `references/commands.md` §1-2.
- Command options are the fields of the `#[derive(SlashCommand)]` struct, read through `self` in the handler. Each field's description is `cmd.<path>.opt.<name>.description` in `locales/en-US.yaml` (write `#[option(..)]` only for other arguments such as `autocomplete` or bounds), its localized names `cmd.<path>.opt.<name>.name` and choice labels `cmd.<path>.opt.<name>.choice.<value>`; `Option<T>` fields (optional) come after required ones; bounds use `min_value`/`max_value`/`min_length`/`max_length`; validators are `fn(&T, &CommandCtx) -> Result<(), MessageKey>`; choices come from a `#[derive(Choices)]` enum. Decode errors are typed (`OptionError`, `InvalidOption`), never unwrapped. See `references/commands.md` §3.
- Autocomplete: mark the option `#[option(.., autocomplete)]` and add the paired `#[autocomplete(field)] async fn x(ctx: AutocompleteCtx, typed: &str, filled: Partial<Self>) -> HandlerResult<Suggestions<T>>` method (`T` = the field's type) to the command's `impl` (see `/dashboard`'s `module` option). `typed` is the raw, possibly partial text, `filled` is untrusted; return `(value, label)` pairs collected into `Suggestions<T>`, capped at 25 in the query. Noctis sends them: never call `respond` there, and there is no defer (2.5 s budget). Re-validate the value in `handle`. Noctis sends at most 25 suggestions, cuts labels over 100 with `…`, drops values Discord would reject (each with a warning), and answers an empty list on error, panic or after 2.5 s (Autocomplete Error Sink). See `references/commands.md` §4.
- Command metadata goes in the attribute: `permissions = MANAGE_GUILD | BAN_MEMBERS` (twilight `Permissions` names, `ADMINISTRATOR` for admin-only), `contexts = [Guild]`, `integration_types = [GuildInstall]`, `nsfw = true`, and `guilds = [<id literal>]` for a guild-scoped command (which then takes no `contexts`/`integration_types`, META-03); unset means omitted, and the values belong to the base command (META-02). Context menus are `#[derive(UserCommand)] #[user_command("Show profile", key = "show_profile")]` / `#[derive(MessageCommand)] #[message_command("Quote", key = "quote")]` unit structs (`key` localizes the name from `ctxcmd.<key>.name`) whose handler is `async fn handle(self, ctx: CommandCtx, target: ResolvedUser | ResolvedMessage[, Ext<T> …][, r: CommandResponder]) -> HandlerResult<R>` (answering like a slash Command): names 1-32 characters (CTX-01), no description or options (CTX-02), same metadata arguments; a missing target is a typed `MenuTargetError`. See `references/commands.md` §1 and §5.
- Answer a Command with `ctx.respond(msg)` or `ctx.reply_text(key)` (or by returning its message: sent as the reply, or as an edit of the original after a `defer_reply`/`reply`); take `r: CommandResponder` (after `ctx` and the path, before the options) only for follow-ups or several messages (slow handlers need no manual `defer_reply`: the auto-defer acknowledges them at `.ack_deadline(..)`, default 2000 ms, and the late answer edits the original), and end with `Ok(acked.done())`. Declare what a handler answers with once, at registration, never per call: `response = public` (default) or `ephemeral` on commands and context menus, `response = update` (default) or `ephemeral`/`public` on a component's kind attribute or on `#[modal(.., response = ..)]` (a slash-opened modal's submit has no message, so under `update` a returned message is a new public reply); it shapes the auto-defer and the default of `reply`/`defer_reply`; `reply_as`/`defer_reply_as` override it for one response, and `r.fetch_reply()` reads the reply message back; `follow_up(msg, Visibility::…)` picks each follow-up's visibility, and no edit changes it. Handle every `ResponderError` with `?`; failures reach the `Command` Error Sink. Run a Command from an event handler (prefix commands) only through `ctx.dispatcher().run_command(CommandInvocation::new(..))`, which replies to the message and cannot be ephemeral. See `references/responder.md` §1-4.
- A failing Command already answers the user: `Err(..)` or a panic shows one ephemeral notice (`noctis.error.generic`, or the key of `HandlerError::with_message(key)`; after a `defer_reply` the loading message is deleted first) and goes to the `Command` Error Sink with the full error logged. Return `HandlerError::user(key)` for known conditions (guild only, not found): only the notice and a `debug` log, no sink; failed option validators behave the same. Never send your own error reply or `unwrap` to bail out. Keys resolve from the catalogs registered with `.locales(strings::catalog())` (and any `Module::locales`); a key no catalog defines renders the generic text with a `noctis::i18n` warning. See `references/responder.md` §5.
- Every interaction handler auto-defers by default (`auto_defer = true`); a handler that opens a modal (a Command or a button) must declare `auto_defer = false` and take the `Manual` responder: `#[command(.., auto_defer = false)]` with `r: CommandResponder<Manual>`, or `#[button("id", auto_defer = false, defaults(..))]` with `r: ComponentResponder<Manual>`, returning `Ok(r.show_modal(form).await?.done())`. One without the other, or `show_modal` on an auto-defer responder, is an `[INT-05]` compile error (`show_modal needs auto_defer = false on this handler`). A modal submit may declare `#[modal(.., auto_defer = false)]` too, and then takes `ModalResponder<Manual>` (required exactly with that flag, `[INT-05]` otherwise) and answers within 3 s itself; modal submits never open a modal (`ModalResponder` has no `show_modal`) and autocomplete takes no `auto_defer`. It gets no auto-defer, so open the modal before any slow work. After 15 minutes only public messages with a known id can still be edited or deleted (bot token); follow-ups and ephemeral messages are `ResponderError::TokenExpired`, and a user-install-only interaction sends at most 5 follow-ups (`FollowupCap`). See `references/responder.md` §2 and §4.
- Commands of every Module merge per scope at `App::build` (one base word = one Discord command). A base or group takes its description from `cmd.<path>.description` in its catalog's default-locale file (so `/setup` needs no `.base`); declare shared base metadata once with `Module::base(name, BaseMeta::new()..)`; leaves under one base must agree on metadata or the base declares it. Fix a `BuildViolation::Command` by its rule id and the Modules its notes name; never rely on the description fallback (it logs a `noctis::registry` warning). See `references/commands.md` §1 and §6.
- Dynamically built Command Patterns are checked with `noctis::rules::command::{validate_pattern_spacing, expand, validate_tree}` before registering; never hand-split patterns. Dynamically declared options go through `noctis::rules::command::validate_options` and `measure_options` (as `with_options(opts.len(), measure_options(&opts, &limits))`) before registering.
- Dynamic component trees, modals, attachments and webhook names can be pre-checked with `noctis::rules::{component, modal, attachment, message}` (`validate_components`, `validate_modal`, `validate_attachments`, `validate_rendered_image_alt`, `validate_webhook_name`, `validate_webhook_thread`, `validate_static_components`, …), whole messages and runtime-built `noctis::ui::Modal`s with `noctis::ui::validate(&mut msg, &limits)` / `noctis::ui::cost(&msg, &limits)` (`validate` also takes a `Modal`), and autocomplete responses with `noctis::rules::command::validate_autocomplete`; never hard-code their limits. Write fixed-shape trees with `noctis::components!`, literals with `label!`/`placeholder!`/`content!`/`alt!`/`rgb!`, and modal forms with `#[derive(Modal)]` plus `#[derive(Choices)]` option sets (all checked at `cargo check`); decode modal submissions with `ModalForm::from_json` and handle every `SubmitError` (never unwrap untrusted input).
- Custom Payload field types implement `noctis::codec::{Field, FieldDecode}` and are tested with `noctis::codec::check::{assert_round_trip, assert_worst_case}` (see `references/routes-payloads-refs.md` §2); never hand-escape field text. Only `Option` fields may be appended to a Payload without a schema bump, since missing trailing fields decode as `None` through `FieldDecode::absent`; never override `absent` on your own types.
- Components are structs whose derive names the kind: `#[derive(Button)]` with `#[button("id", args…, defaults(style = Secondary, label = keys::COMMON_REFRESH))]`, `#[derive(StringSelectMenu)]`/`#[string_select(..)]`, `UserSelectMenu`/`user_select`, `RoleSelectMenu`/`role_select`, `MentionableSelectMenu`/`mentionable_select`, `ChannelSelectMenu`/`channel_select`, and `#[derive(Modal)]`/`#[modal("id", .., defaults(title = keys::PROFILE_BIO_MODAL_TITLE))]` (fields without an input attribute are its Payload; a built value pre-fills the inputs: `None`, `""`, `vec![]` and `false` send nothing). `defaults(..)` is mandatory (Button: `style` and `label` or `emoji`; selects: `placeholder`; modal: `title`; a `defaults` text (`label`, `placeholder`, `title`) is a `keys::` path, a locale key the Responder resolves in the response locale and validates after resolving, or a string literal for fixed text checked at `cargo check`; input attribute texts such as `#[text_input("Bio")]` are literals only, so localize them per render through `XOverrides { field: InputOverrides { label: Some(keys::X.into()), .. }, .. }` (see `handlers::bio_modal`); build with `X { .. }.build()` and override one render with the setters `.label(..)`, `.style(..)`, `.disabled(..)`, `.placeholder(..)`, `.options(..)`, `.default_values(..)`, … or several fields at once with `.overrides(ButtonOverrides { label: Some("Again".into()), disabled: Some(true), ..Default::default() })` (`StringSelectOverrides`, `UserSelectOverrides`, `RoleSelectOverrides`, `MentionableSelectOverrides`, `ChannelSelectOverrides`; the later call wins); every override text is a `Text`: a literal or a `MessageKey`, which the Responder translates in the response locale before sending. A modal's `X { .. }.build()` is a `ModalBuilder<X>` with `.title(..)`, `.value(X::FIELD, v)` and `.overrides(XOverrides { field: InputOverrides { label: .., description: .., placeholder: .. }, .. })`; `X::blank(<payload fields>)` is an `X` when every input field has an empty value (`Option`, `Vec`, `String`, `bool`), so `X { bio: v, ..X::blank(user) }` works, else a `ModalBuilder<X>`; `show_modal` takes either. A pre-fill over a Text Input's `max_length`, or more defaults than `max_values`, is `ResponderError::Invalid` with nothing sent. Link buttons are `LinkButton::new(url)`. Arguments after the id: the codec arguments `by_ref`, `overflow = spill`, `schema = n` and `signed` (every select carries its nonce; `view` and the bare `select` are withdrawn: never use them), and the runtime arguments `response = update | ephemeral | public` (default `update`: the auto-defer is type 6 and a returned message updates the clicked message; `ephemeral`/`public` answer with a new message) and `auto_defer = true | false` (default `true`; `false` only for a component that opens a modal, with `ComponentResponder<Manual>`, or a modal submit that answers itself, with `ModalResponder<Manual>`), both also on `#[modal(..)]`, plus `ttl = "15m"` (units `d`/`h`/`m`/`s` in that order, 1 s..=365 d; default `.ref_ttl(..)`, 24 h) and `one_shot` (the first click consumes the Ref: confirmations) on by-Ref Routes only (`by_ref` or `overflow = spill`); and the Route Guards on every kind attribute (`#[modal]` included): `owner = field` (an `Id<UserMarker>` Payload field; only that user may click or submit), `permissions = MANAGE_GUILD | BAN_MEMBERS` (the member's resolved channel permissions; `ADMINISTRATOR` passes, a DM is denied) and `guard = path::to::fn` (an `async fn(ctx: &ComponentCtx, this: &Self) -> HandlerResult<Access>`, `&ModalSubmitCtx` on a modal; return `Access::Allow`, `Access::deny()` or `Access::Deny(key)`). Guards run owner, permissions, custom, after the Middleware and before the handler; a denial is a localized ephemeral notice (`noctis.guard.*`) and the handler never runs; a denied `one_shot` Ref is restored. They still don't replace authorization checks in the handler for anything sensitive. Rate limits: `rate_limit(user | member | channel | guild | message, n, per = "10s"[, manual])` on any kind attribute and on `#[command]`/`#[user_command]`/`#[message_command]` (repeatable, one per scope; `message` not on `#[command]`/`#[user_command]`) refuses the run before the auto-defer with the localized `noctis.rate_limited` notice; a `manual` limit counts only `ctx.rate_limits().hit(RateScope::User)` (see `BioForm`), `block`/`extend`/`reset` adjust it, and an `#[on_rate_limited]` method or `.rate_limited_handler(f)` replaces the notice (`references/modules-middleware-ratelimits.md` §7). Never hand-roll cooldowns in handlers. A component or modal handler deletes Refs of a reusable flow by returning `(message, RefOps::new().delete(r))`, with `ctx.current_ref()` for the clicked one. A component or modal handler takes `(self, ctx: ComponentCtx[, Ext<T> …][, r: ComponentResponder])` / `(self, ctx: ModalSubmitCtx[, Ext<T> …][, r: ModalResponder | ModalResponder<Manual>])`; `update` on a slash-opened modal's submit is `ResponderError::UpdateUnavailable`. `signed` Routes need `NOCTIS_PAYLOAD_KEY` (64 hex digits; `.env` gets one on first run). The derive proves at compile time that every `custom_id` fits 100 characters (`[CID-01]`); keep each component's width line (from `cargo test --release -- --nocapture noctis_route_width`) in its doc comment. Small closed sets are `#[derive(PayloadEnum)]` unit enums (one character, at most 62 variants; append variants, never reorder or remove them without bumping `schema`). `#[derive(Payload)]` is only for the Payload of a hand-written `Route`.
- Stale and expired ids: a component from before a `schema` bump (or another shape change) or with a missing Ref never reaches `#[handler]`. Give the struct an `#[on_stale] async fn restart(ctx: ComponentCtx) -> HandlerResult<V2Message>` and/or an `#[on_expired] async fn expired(ctx: ComponentCtx, expired: Expired) -> HandlerResult<V2Message>` method (no `self`; same `response`/`auto_defer` as the Route) that re-renders the View from scratch (see `SetupState`), or one App-wide `.expired_handler(f)`; without either the user gets the `noctis.expired` notice. Only appending `Option` fields keeps old ids decoding; any other Payload change bumps `schema`. See `references/routes-payloads-refs.md` §6 and §8.
- Module ids are full paths: a root Module has one segment (`profile`) and a nested one adds exactly one (`Module::new("profile/badges")` inside `profile`, as `src/modules/profile/mod.rs` does); ids use `a-z`, `0-9`, `_`, `-` and are unique per App. Fix a `BuildViolation::InvalidModuleId` by its `ModuleIdError` reason and a `BuildViolation::DuplicateModule` by renaming or mounting the tree once; the id is the `module` field of spans and `ErrorReport`s. See `references/modules-middleware-ratelimits.md` §1.
- Boot Flags pick feature sets at start-up: flag a Module with `Module::new("x").flags(["beta"])` or one registration with `flags = ["beta"]` on its kind attribute (`#[command(..)]`, `#[user_command]`/`#[message_command]`, `#[event(..)]`, `#[button]`, the select attributes, `#[modal]`); a flag is 1-32 characters of `a-z`, `0-9`, `_`, `-` (`all` and `none` are reserved; a bad literal does not compile, a bad `Module::flags` entry is a `BuildViolation::InvalidBootFlag`). An unflagged item always exists; a flagged one exists when the selection is `all` (the default) or holds any of its flags; a pruned Module drops its whole subtree (here `profile/badges` carries `badges`). The selection comes from `--features a,b|all|none` (wins) or `NOCTIS_FEATURES`, both read by `App::from_env()` before `build()`, or `AppBuilder::boot_flags(BootFlags::..)`; a selected flag nothing declares is a `BuildViolation::UnknownBootFlag`, and `run` rejects a `--features` that differs from the built selection with `CliError::BootFlagsMismatch`. Unselected registrations are not dispatched, add no intents and are not published (a Publish of a subset deletes the unselected remote Commands). See `references/modules-middleware-ratelimits.md` §2.
- Switch Modules on and off at run time with `ctx.modules()` (`App::modules()` outside a handler): `set_enabled("profile", ModuleScope::Guild(guild), false).await?` (or `ModuleScope::Global`; `reset(id, scope)` removes a guild override), and `is_enabled("profile", ctx.guild_id())` reads the cached snapshot with no I/O (DMs use `Global`). Ids are the exact `Module::new(..)` ids the Boot Flags kept; anything else is `ModuleStateError::UnknownModule`. Enablement is AND over the Module tree, so disabling `profile` also disables `profile/badges`. A disabled Module's Commands, components and modals answer the ephemeral `noctis.module.disabled` notice before any handler, Middleware or Guard, and its event handlers are skipped. Other processes see a toggle within `.module_state_poll(..)` (default 5 s), so share one `ModuleStateStore` (`.module_state_store(..)`, same `app_id`) across a Cluster. A toggle never publishes: re-run `--publish` to drop a disabled Module's guild-scoped Commands from that guild (global Commands stay). See `references/modules-middleware-ratelimits.md` §3.
- Multiple Apps in one process (white-label bots): build each with its own `App::builder()` chain, its own `.token(..)` and a distinct `.app_id(..)` (`[a-z0-9-]{1,32}`; two Apps must never share an id), on one `Runtime`, and run them with `tokio::try_join!(main.run(), acme.run())`. The same Module tree mounts on both; restrict a Command to some Apps with `apps = ["noctis-template"]` on `#[command]`/`#[user_command]`/`#[message_command]` (a bad id does not compile) or a whole Module with `Module::new("x").apps(["acme"])` (a bad id is a `BuildViolation::InvalidAppRestriction`); a restricted item exists only on Apps whose effective App id is listed, like a Boot Flag (here `/setup start` is main-App only). Serve guilds selectively with `.guild_access(GuildAccess::allow([guild]))` or `GuildAccess::deny([..])` (`noctis::ports::memory`): a refused guild gets the ephemeral `noctis.module.disabled` notice, no handler, Middleware or report; events from it run no handler and `Dispatcher::run_command` returns `DispatchError::GuildNotServed`; DMs are always served; Publish ignores the list. Apps share an Adapter's data only when it is passed as `Shared::new(adapter)`. See `references/app-and-sharding.md` §10.
- One handler per Route id per App: add each component or modal struct with `.add::<X>()` to exactly one mounted Module (a second registration of the id is a `[CID-04]` `BuildError`), and never rename a released Route id. A Module whose Views render another Module's Route declares it with `Module::new("dash").uses::<X>()`, so `build()` fails (``[CID-04] Module `dash` uses Route …, but no mounted Module handles it``) when the handling Module is not mounted. Clicks and modal submits dispatch to the `#[handler]`, which answers by returning a message or through its responder; an id that reaches no handler gets a generic ephemeral notice (CID-06). See `references/routes-payloads-refs.md` §1.
- Gateway events are `#[derive(EventHandler)] #[event]` unit structs whose handler is `async fn handle(self, ctx: EventCtx, event: <noctis::events payload>[, Ext<T> …]) -> HandlerResult<()>`, added with `Module::add::<X>()` and mounted with `AppBuilder::module`; see `references/modules-middleware-ratelimits.md` §4. Their intents are derived: never request a non-privileged intent just for a handler, request privileged ones (`GUILD_MEMBERS`, `GUILD_PRESENCES`, `MESSAGE_CONTENT`) with `.intents(..)`, and fix a `[GW-05]` `BuildError` by requesting the intent it names and enabling it in the Developer Portal. Keep handlers idempotent; mark `ordered` only when per-guild order matters.
- Shared pre- and post-handler logic is Module Middleware, never copied into each handler: `Module::new("x").before(Middleware::before(f).provides::<T>())` with `async fn f(ctx: BeforeCtx) -> HandlerResult<Flow>` that `ctx.insert(T)`s and returns `Flow::Continue`, or `Flow::Stop(Some(key))` to deny with a localized ephemeral notice (never `Stop(None)` for a denial); `.after(Middleware::after(g))` with `async fn g(ctx: AfterCtx)` runs after every outcome (`ctx.outcome()`). The parent Module's Middleware run first, each Module's in registration order (after-Middleware in reverse); scope I/O Middleware with `.skip_events()` (or `.events_only()`). Handlers take the values as `Ext<T>` (a `BuildViolation::MissingExtension` when no Middleware on the Module path `provides::<T>()`) or `Option<Ext<T>>`; Extensions live for one run and are never stored (see `src/modules/dashboard/mod.rs`'s `guild_only` and `references/modules-middleware-ratelimits.md` §5). Nothing runs for autocomplete or the stale/expired hooks.
- Post through webhooks with `ctx.webhooks()` (`App::webhooks()` outside a handler): `create(WebhookChannel::new(id, kind), webhook_name!("…"))` once and store its `id()` and `token()` like a password (never log or show the token), rebuild it with `owned(id, token)?.in_channel(kind)`, and `send` any View; a webhook the bot does not own is `foreign(id, token)?` and sends only a `noctis::ui::StaticMessage` (`StaticComponents`/`StaticContainer`/`StaticSection`/`StaticActionRow`, Link buttons only; `[WH-02]` at `cargo check`). Forum and media channels need `.thread(..)`. A webhook failure in a side effect is a `tracing::warn!`, not a failed interaction (see `src/modules/setup/handlers.rs` and `references/responder.md` §7).
- Handler failures go to Error Sinks: route an origin with `.error_sink(ErrorOrigin::…, sink)` (see `src/observability.rs` and `references/modules-middleware-ratelimits.md` §6); a sink is synchronous and must not block, so forward to a channel for I/O. noctis emits only the metrics listed in `noctis::observe::METRICS` (`references/app-and-sharding.md` §11); install your own `tracing` subscriber and `metrics` recorder, and never put ids or free text in metric labels.
- The bot's status is a `noctis::gateway::Presence`: set the identify presence with `.presence(..)` in `configure`, change it at run time with `app.presence().set(..)`/`.set_shard(n, ..)`, and send gateway commands (`ctx.gateway().request_guild_members(MemberRequest::..)`) only through the `GatewayHandle`; every refusal is a typed `GatewayError` (out of Shard Range, GW-04 send budget, GW-07 `RATE_LIMITED`, missing intent, timeout), never a silent drop (`references/app-and-sharding.md` §6).
- Prefix commands are opt-in (Noctis feature `prefix`, this template's `prefix` feature, off by default): `.plugin(noctis::prefix::PrefixPlugin::new("!").command::<Profile>())` plus `.intents(Intents::MESSAGE_CONTENT)` (privileged; without it the build fails with `[GW-05]` `MissingIntent`) makes `!profile @user` run the same `#[handler]`; a bad argument is the same `OptionError` as a slash decode (public validation notice, Command Error Sink), and Commands with `permissions`, `nsfw = true` or `channel_types` cannot be opted in (`references/commands.md`, "Prefix commands").
- A Cluster splits the shards by configuration only: each process sets `NOCTIS_SHARD_RANGE=start..end` (half-open) with the same `NOCTIS_SHARD_TOTAL`, all processes share one `IdentifyQueue` and point at one shared rate-limit proxy with `NOCTIS_HTTP_PROXY` (without it, `run` logs an RL-02 warning), and exactly one sets `NOCTIS_PUBLISHER=true`; handlers never change (`references/app-and-sharding.md` §4).
- Shutdown is graceful: `app.run()` stops on Ctrl-C/SIGTERM and gives queued events and running handlers `.shutdown_grace(..)` (default 10 s, `NOCTIS_SHUTDOWN_GRACE`) before cancelling them (`ReportKind::Cancelled`); keep handlers cancel-safe at every `.await`, never block a thread inside one, and use `app.run_until(fut)` in tests instead of signals. A `RunError::AllShardsEnded` from `run` means every shard closed fatally: read the `shard closed fatally` logs (see `references/app-and-sharding.md` §8).
- Discord HTTP goes through the App's one client (`ctx.http()`), which a built-in edge keeps warm with HTTP/2 PINGs and redials when it dies; never poll an endpoint (such as `GET /users/@me`) to keep HTTP warm, and tune only through `.http(HttpConfig)` (`references/app-and-sharding.md` §5). For an endpoint twilight does not model, `ctx.http().raw(method, path)` is the last resort (same client, rate limits and proxy; `references/components-v2.md` §11b); never build a second HTTP client. Every request is bounded by `.http_timeout(..)` (default 10 s). Handle `RateLimited` (`ResponderError::RateLimited`, `WebhookError::RateLimited`, `RawHttpError::RateLimited`; `ctx.http()` errors via `noctis::http::RateLimited::from_http_error`): wait at least its `retry_after`, never retry in a loop. The initial interaction response (respond or defer) is the exception: noctis retries it once when `retry_after` fits the ack deadline, else it fails as `AckDeadlineMissed`, never `RateLimited`. An interaction must be acknowledged within 2.9 s of receipt (`AckDeadlineMissed`): defer before slow work.
- Rendered images are Templates: a `#[derive(Template, Serialize, Deserialize)]` struct with `#[template(id = "feature.card", version = 1, size = (w, h), format = Png)]` (bump `version` whenever the data or the look changes) plus `impl TemplateView for X { fn view(&self, frame: Frame) -> Node { view! { .. } } }`, registered with `Module::new("x").template::<X>()` (two Templates with one id are a `BuildViolation::DuplicateTemplate`). Template data never holds a `HashMap`/`HashSet` (use `BTreeMap`/`Vec`). Literal classes (`tw="…"`, `tw!("…")`) are checked at `cargo check` (`[TW-01]`) against `noctis-theme.css` (`[TW-02]`); values chosen at run time go through `Style` setters (`width_pct`, `color_rgb`, …), user text only as a `{text}` child, and never into `Classes::dynamic`. Render inside the handler with `ctx.render(card).await?` (the App installs the Renderer with `.theme(noctis::image::theme!())`/`.image(ImageConfig)`); a `RenderError::QueueFull` (found with `err.as_error().downcast_ref::<RenderError>()`) deserves a "busy, try again" notice, not an error. Renders fit the upload budget automatically (fps, then size, then quality, then a still frame); `RenderError::OverBudget` means the image cannot shrink enough, so make the Template smaller or simpler. Per-job caps (`ImageConfig::caps(RenderCaps::new())`: 4 MP per job, 1 MP per frame, 90 frames, 6 s) reject a job before it is queued with `RenderError::OverCap { cap: RenderCap, .. }`; a still weighs 1 queue unit and an animation `ceil(frames / 8)`, a quarter of the queue is reserved for stills, and dropping the `ctx.render` future cancels the render (wrap it in `tokio::time::timeout` for a deadline). Animated Templates add `animation(duration_ms = .., fps = ..)` (animated WebP by default; `Gif`/`Apng` need the `image-gif` feature), or animate one call with `ctx.render_with(t, RenderOptions::new().animation(AnimationSpec::new(..)))`; `ctx.render_report(t, RenderOptions::new())` returns a `RenderReport` with `format` and `settings_used`. The fps is capped per format (GIF 50, WebP/APNG 90; `RenderError::OverCap { cap: RenderCap::Fps, .. }`), and every frame root keeps the Template's size (`RenderError::SizeMismatch`). CSS animations are `animate-spin|ping|pulse|bounce`, `animate-<token>` for a theme `--animate-<token>` whose `@keyframes` the theme defines, or `animate-[<keyframes>_1s_…]`; a still draws them at 0 ms. Text needs a font: this template enables `default-font` (bundled Inter 4.1, OFL-1.1, the last-resort family `"Inter"`); extra fonts go in priority order with `ImageConfig::new().font(Font::from_static(include_bytes!(..)).family(..).unicode_range(..))` (later fonts are fallbacks for missing glyphs, no Template change), and every App on one `Runtime` must register the same font list (else `ResourceConflict` naming `FontRegistry`); a Template with no font at all fails `App::build` with `[IMG-01]`. Static images are `const LOGO: StaticImage = StaticImage::new("logo", include_bytes!("../assets/logo.png"));` (PNG/JPEG/WebP, at most 16 MP, id `[a-z0-9]([a-z0-9._-]*[a-z0-9])?`), registered with `ImageConfig::image(LOGO)` and drawn with `<img src={LOGO} tw=".." />`; an unregistered one fails the render with `RenderError::UnknownImage` ([IMG-02]). `<svg>` is not supported. Remote images (avatars, guild icons, allow-listed URLs) are declared as `#[asset] avatar: RemoteImage` fields (`Option<RemoteImage>`/`Vec<RemoteImage>` too; `#[asset(required)]` fails the render with `RenderError::RemoteImage` instead of drawing the fallback), built with `RemoteImage::avatar(&user, 256)`, `RemoteImage::guild_icon(&guild, 128)`, `RemoteImage::url(..)?` or `RemoteImage::placeholder()` (no fetch: use it in tests), and drawn with `<img src={&self.avatar} />`; Noctis fetches them before the render from the allow-list (the Discord CDN by default; `ImageConfig::remote(RemoteConfig::new().allow_origin("https://…"))`), caches them in the `AssetStore` and logs a `noctis::image` warning when one falls back ([IMG-03]). Identical renders are deduplicated and served from the App's `RenderCache` (errors and fallback renders are not cached), so bump the Template's `version` whenever its view changes (`references/images.md` §9). Discord custom emoji (`<:name:id>`) in Template data fields render inline as fetched images automatically (never write such a token in literal `view!` text: a compile error), and Unicode emoji draw in colour only with the `image-emoji` feature (Twemoji, CC-BY-4.0: credit it when the bot posts such images) ([IMG-04]). See `references/images.md`.
- Port keys are namespaced by `app_id`; share one only with `Shared::new(..)`; store bot data through `ctx.kv()` (see `references/adapters.md` §3 and §6).
- Discord resources (guilds, channels, roles, members, users, messages) come from `ctx.cache()` on every context (`CommandCtx`, `ComponentCtx`, `ModalSubmitCtx`, `AutocompleteCtx`, `EventCtx`, `BeforeCtx`/`AfterCtx`): async getters (`guild`, `channel`, `role`, `member`, `user`, `message`, `channel_ids`/`role_ids`/`member_ids`, `channels`/`roles`/`members`) return owned twilight values, never a guard; `Ok(None)` means not cached (fall back, never `unwrap`), and `CacheError::Disabled(CacheDisabled { resource })` means that resource is not configured. The default caches `GUILD | CHANNEL | ROLE`; change it with `.discord_cache(DiscordCacheConfig::default().with_resources(DiscordCacheResources::USER))` (`noctis::DiscordCacheConfig`, `noctis::DiscordCacheResources`), turn it off with `DiscordCacheConfig::none()`, and swap the backend with `.discord_cache_backend(..)` (an `Arc` shares one across a Cluster). `MEMBER` needs `.intents(Intents::GUILD_MEMBERS)` (else `BuildViolation::MissingCacheIntent`, `[GW-05]`). See `references/adapters.md`.
- Storage goes through ports (`noctis::ports`), never a `static` map: the bounded defaults live in `noctis::ports::memory` (`MemoryCacheStore`, `MemoryDiscordCache`, `MemoryIdentifyQueue`, …; see `references/adapters.md` §1.1), and a custom Adapter implements the port trait the way `src/adapters/bounded_cache.rs` does (verbatim keys, opaque `Bytes`, atomic ops, bounded).
- Inside the noctis-rs monorepo this crate is standalone (`[workspace]` in its `Cargo.toml`); the monorepo root `Cargo.toml` must keep `exclude = ["examples/project-template"]`. After copying it out, switch the `noctis` dependency to the crates.io form shown in `Cargo.toml`.
