## How to read this catalog

### Enforcement tiers

Noctis checks every rule at the **earliest point where all the inputs are known**:

| Tier | When | Applies when | Failure looks like |
|---|---|---|---|
| **Compile-time** | `cargo check` (AD-4: a check that fires only under `cargo build` doesn't count) | The input is static: string literals in attributes or macros, field types of a `derive`d struct, const generics, the shape of a typed component tree. | `compile_error!` from a proc macro, a failed free `const _` item over a concrete type, or a missing trait impl whose `#[diagnostic::on_unimplemented]` message starts with the rule id. |
| **App-build** | `App::builder()...build()`, before any gateway connection or HTTP write | The rule depends on combining Modules (merging Commands across Modules, global counts, Route uniqueness, intents versus handlers). | `Err(BuildError)` that lists **all** violations (not just the first), each naming the rule ID, the Modules involved and the actual value. `--publish --dry-run` runs the same checks. |
| **Runtime** | While handling an interaction or sending a request | The data is genuinely dynamic: user input, database rows, `Vec`s of unknown length, timers, Discord-side quotas. | A typed `Error` returned before the request is sent (never a 400 from Discord, never a panic). Some rules have a lenient mode (truncate with `…`) as FR-24 allows. |

**Compile-time (by construction)** marks a rule that holds because the API can't
express the violation: the type has no such field, method, variant or constructor
(`V2Message` has no `content`; `Responder<Acked>` has no `reply`). rustc's own error
(E0599, E0609, E0382, E0308, …) rejects the attempt, and that error can't name the
rule. Its evidence is a `compile_fail` doctest or a trybuild fixture whose source
carries `// [<RULE-ID>]` on the offending line (AD-4). Every other Compile-time rule
is diagnosed by Noctis (proc macro or `#[diagnostic::on_unimplemented]`), and its
fixture's `.stderr` contains `[<RULE-ID>]`.

A rule often has several tiers. For example, a button label written as a literal is
checked at compile time, and a label built from a database row is checked at runtime by
the same validator code. The **Enforcement** column lists the tiers in the order they
apply. "Compile-time (literal) / Runtime (dynamic)" means the macro checks literals
and the runtime validator checks everything else.

### Confidence markers

- **[D]**: stated in Discord's official docs (linked).
- **[C]**: observed by the community or other libraries (discord.js, JDA, Discord.Net),
  enforced by the API but not written in Discord's docs.
- **[U]**: **unconfirmed exact value or counting unit.** Noctis uses the conservative
  interpretation and keeps the value configurable. See
  [Unconfirmed values](#unconfirmed-values).
- **[N]**: a Noctis design choice, not a Discord rule.

### Rule IDs

Every rule has a stable ID (for example `CMD-03`). Compile errors, `BuildError`
variants, runtime errors and trybuild fixtures all cite this ID, so a failing build
points straight back to this file.
`noctis_rules::RuleId` holds exactly these ids (a test compares it with this file), and every `Limits` field names its rule id.

## 1. Chat-input command names and descriptions

| Rule | Limit/value | Source | Enforcement | How |
|---|---|---|---|---|
| **CMD-01** Name charset | Must match `^[-_ʼ\p{L}\p{N}\p{sc=Deva}\p{sc=Thai}]{1,32}$` with the Unicode flag. Note: the official regex allows `ʼ` (U+02BC, modifier letter apostrophe), **not** the ASCII `'`. Applies to command, subcommand group, subcommand and option names. **[D]** | [AC §Naming](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-naming) | Compile-time (literal) / App-build (names from the merged locale catalogs; `LocaleSource` overlays never carry reserved keys (Story 11.5)) | `#[command("…")]` / `command!` splits the Command Pattern into words and matches each against the regex. The check lives in `noctis-rules` (which may depend on `regex` with Unicode tables); the proc macro and App-build call the same function. Error spans point at the pattern literal. Whitespace other than U+0020 between words (`"config\tset"`, U+00A0) is CMD-01 too, reported by `validate_pattern_spacing` before expansion. With the `i18n` feature and a default-locale file, a Command word `name`, `description` or `opt` is CMD-01 as well (it would be ambiguous in the `cmd.<path>` keys; fixture `tests/ui-i18n/cmd/CMD-01_reserved_locale_word.rs`). Localized names (`cmd.<path>.name`, `cmdword.<word>`, `cmd.<path>.opt.<o>.name`) follow this rule through LOC-02. |
| **CMD-02** Name length | 1-32 characters per word **[D]** (counting unit **[U]**: Noctis counts both Unicode scalar values and UTF-16 units and takes the larger) | [AC §Command structure](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-structure) | Compile-time (literal) / App-build (loaded locales) | Same macro pass as CMD-01. Leading, trailing or doubled spaces are empty words (`"config  set"`, `" ping"`), rejected by `noctis_rules::command::validate_pattern_spacing` before expansion (note `empty word at byte N`). |
| **CMD-03** Lowercase | If a letter has a lowercase variant, the lowercase form must be used. Uncased letters (e.g. CJK, Devanagari) are allowed. **[D]** | [AC §Naming](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-naming) | Compile-time (literal) / App-build (loaded locales) | Macro checks `c.to_lowercase() == c` for every `char`. The error suggests the lowercased word. |
| **CMD-04** Description length | 1-100 characters for `CHAT_INPUT` commands, subcommands, groups and options **[D]** | [AC §Command structure](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-structure) | Compile-time (literal; default-locale file with the `i18n` feature) / App-build (merged and non-default locales) | Source per AD-16: the literal `description = "…"` without the `i18n` feature; with it and a default-locale file (`#[command(.., locales = "<dir>", default_locale = "<code>")]`, default `locales` / `en-US`), `cmd.<path>.description` per expanded path and `cmd.<path>.opt.<o>.description` per option, where a differing literal is a compile error (`description differs from …`) and a missing key without a literal is the missing-description error with a `not found as …` note (fixtures `tests/ui-i18n/cmd/CMD-04_description_missing_in_locale_file.rs`, `CMD-04_literal_differs_from_locale_file.rs`). A base or group nobody describes takes `cmd.<path>.description` from its catalog's default-locale file at App-build, without a warning. A `Module::base`/`Module::group` description, a file-less or runtime handler description (per path for a Pattern), or a runtime option description, and the handler fallback of an undescribed base or group, that differs from the value sent for its owner catalog's default locale (that locale's file, else its sibling's, e.g. `en-GB` for `en-US`; other locales are never compared) for `cmd.<path>.description` / `cmd.<path>.opt.<o>.description` fails `App::build` as one `BuildViolation::Command` CMD-04 per key (``description differs from `<key>` in catalog `<origin>` (<file locale>)``, the file's text and a `declared by` note; help `make them equal or remove the declaration`), so `description` and the default locale's `description_localizations` never disagree (unit tests `cmd_04_declared_description_differs_from_catalog`, `cmd_04_declared_description_differs_from_sibling_default`). Doc comments are rustdoc only. The macro measures the description; a missing one is a compile error (Noctis never sends tescord's `"..."` placeholder **[N]**). `Module::base(name, BaseMeta::new().description(..))` and `Module::group(path, description)` descriptions are measured at App-build (`declared by` note). A base or group nobody describes takes the description of the handler below it from the lexicographically smallest Module id (then the smallest path), with a `noctis::registry` warning; that fallback is counted by CMD-05. |
| **CMD-05** Per-command size budget | Combined `name` + `description` + choice `value` of the command, all options (incl. subcommands and groups) and all choices ≤ **8000** characters. With localizations, only the **longest** variant per field (including the default) counts. **[D]** (counting unit **[U]**) | [AC §Slash Commands](https://discord.com/developers/docs/interactions/application-commands#slash-commands) | Compile-time (one pattern, static locales) / App-build (after merging Modules, or with the merged locale catalogs; `LocaleSource` overlays never carry reserved keys (Story 11.5)) | `#[derive(SlashCommand)]` checks the budget of its expanded pattern with `noctis_rules::command::validate_tree` (longest variant per field). Merging changes the total, so `App::build()` recomputes the budget on the merged tree using `max(len(default), len(each localization))` per field. At App-build the localized variants come from the merged locale catalogs (Story 11.4): every LOC-02-valid localized name, description and choice name is passed into the declarations (`CommandDecl::name_localized`, `LocalizedText::localized`, `measure_options` over localized option copies), so the budget counts the longest variant (unit test `cmd_05_counts_the_longest_localization`). `App::build` lowers every Module's descriptors (and `Module::base` / `Module::group` declarations) into `noctis_rules` declarations and runs `noctis_rules::command::validate_merge` once, per scope; each broken rule is one `BuildViolation::Command` whose notes name the Modules and end with the scope (`scope: global` / `scope: guild <id>`). A `contributed by` note lists the subtree's Modules. |
| **CMD-06** Unique option names | `name` unique within each options array **[D]** | [AC §Option structure](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-option-structure) | Compile-time (within one struct) / App-build (merged) | `#[derive(SlashCommand)]` names each option after its field (`r#` stripped) or `#[option(rename = "…")]` and rejects duplicate names at expansion (`noctis_rules::command::validate_options`, note `declared at positions i, j`). Across Modules it is REG-04 (one handler per command path): `App::build` lowers every Module's descriptors (and `Module::base` / `Module::group` declarations) into `noctis_rules` declarations and runs `noctis_rules::command::validate_merge` once, per scope; each broken rule is one `BuildViolation::Command` whose notes name the Modules and end with the scope (`scope: global` / `scope: guild <id>`). |
| **CMD-07** Age-restricted flag | `nsfw: bool` per command. Apps with discovery enabled cannot contain any age-restricted commands. **[D]** | [AC §Age-Restricted Commands](https://discord.com/developers/docs/interactions/application-commands#age-restricted-commands) | Compile-time (type) / App-build (merge conflicts) | `#[command(…, nsfw = true)]` (also on `#[user_command]` / `#[message_command]`) takes `true` or `false`; any other value is a `[CMD-07]` compile error. The value lands in `CommandMetadata::nsfw`. Conflicting values on one base command fail at App-build (FR-9). The discovery restriction is not checkable locally and is only documented. A `Module::base` `BaseMeta::nsfw` declaration is the explicit base value: unset handlers inherit it and set ones must match. |

## 2. Command structure: subcommands, groups and Command Patterns

| Rule | Limit/value | Source | Enforcement | How |
|---|---|---|---|---|
| **CMD-10** Nesting depth | Only `command → group → subcommand`. Groups cannot contain groups; subcommands cannot contain subcommands or groups. A Command Path has at most **3** words. **[D]** | [AC §Subcommands and Subcommand Groups](https://discord.com/developers/docs/interactions/application-commands#subcommands-and-subcommand-groups) | Compile-time | The macro expands the Command Pattern and rejects any expansion with more than 3 words. A `Module::group` / `Module::base` path of more than 3 words is CMD-10 at App-build (`declared by` note). |
| **CMD-11** Name is either a subcommand or a group | One name at one level cannot be both a leaf subcommand and a subcommand group (`config set` and `config set prefix` together are invalid). **[D]** (follows from the option tree: a `SUB_COMMAND` option has no subcommand children) | [AC §Subcommands and Subcommand Groups](https://discord.com/developers/docs/interactions/application-commands#subcommands-and-subcommand-groups) | Compile-time (within one pattern) / App-build (across registrations and Modules) | The macro builds the expansion tree and checks every node. See [Compile-time strategy §3](#3-command-pattern-expansion-and-structural-validation). `App::build` lowers every Module's descriptors (and `Module::base` / `Module::group` declarations) into `noctis_rules` declarations and runs `noctis_rules::command::validate_merge` once, per scope; each broken rule is one `BuildViolation::Command` whose notes name the Modules and end with the scope (`scope: global` / `scope: guild <id>`). |
| **CMD-12** Base command with subcommands is not invokable | Once a command has subcommands or groups, the base command itself cannot be used, and it cannot have its own non-subcommand options. **[D]** | [AC §Subcommands and Subcommand Groups](https://discord.com/developers/docs/interactions/application-commands#subcommands-and-subcommand-groups) | Compile-time (one pattern, e.g. `config (set)?`) / App-build (Module A registers `config`, Module B registers `config set`) | A pattern whose expansions contain both `x` and `x y` is a compile error. Across Modules this is a `BuildError` (FR-9: no silent dropping). `App::build` lowers every Module's descriptors (and `Module::base` / `Module::group` declarations) into `noctis_rules` declarations and runs `noctis_rules::command::validate_merge` once, per scope; each broken rule is one `BuildViolation::Command` whose notes name the Modules and end with the scope (`scope: global` / `scope: guild <id>`). |
| **CMD-13** Max options / subcommands / groups per level | `options` array max **25** at every level (top-level options, subcommands + groups under a command, subcommands under a group, parameters under a subcommand). **[D]** | [AC §Option structure](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-option-structure) | Compile-time (per struct / per pattern) / App-build (after merge) | `#[derive(SlashCommand)]` counts fields. The pattern macro counts distinct children per node. The merged tree is recounted in `App::build()`. `App::build` lowers every Module's descriptors (and `Module::base` / `Module::group` declarations) into `noctis_rules` declarations and runs `noctis_rules::command::validate_merge` once, per scope; each broken rule is one `BuildViolation::Command` whose notes name the Modules and end with the scope (`scope: global` / `scope: guild <id>`). The children violation has a `contributed by` note listing the subtree's Modules; the options one a `declared by` note. |
| **CMD-14** Mixing groups and subcommands | A command may hold groups and plain subcommands side by side. **[D]** | [AC §Subcommands and Subcommand Groups](https://discord.com/developers/docs/interactions/application-commands#subcommands-and-subcommand-groups) | (permitted; no check) | Documented so the validator does not reject a valid tree. |
| **CMD-15** Pattern expansion bound | Noctis caps one Command Pattern at **25** expansions by default (FR-8), configurable with `#[command(max_expansions = n)]`, and rejects patterns where an optional group makes two expansions identical. **[N]** | — | Compile-time (literal patterns) / App-build (dynamically built patterns) | Guards against accidental combinatorial patterns. Expansion order is left to right in declaration order (FR-8). |
| **CMD-16** Command Pattern syntax | A pattern is whitespace-separated words and groups; a group is a whole word `(a\|b\|…)`, optionally followed by `?`, whose alternatives are non-empty single words; no nesting, no `\|` or `?` outside that shape **[N]** | — | Compile-time (literal patterns) / App-build (dynamically built patterns) | `noctis_rules::command::expand` reports the first syntax error with its byte offset. |

## 3. Command options

| Rule | Limit/value | Source | Enforcement | How |
|---|---|---|---|---|
| **OPT-01** Required before optional | Required options must be listed before optional ones. **[D]** | [AC §Option structure](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-option-structure) | Compile-time | `#[derive(SlashCommand)]`: non-`Option<T>` fields are required. | **OPT-02** Option types | `STRING 3, INTEGER 4, BOOLEAN 5, USER 6, CHANNEL 7, ROLE 8, MENTIONABLE 9, NUMBER 10, ATTACHMENT 11` (1, 2 are subcommand/group) **[D]** | [AC §Option type](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-option-type) | Compile-time / Runtime (decoding) | Field type → option type via the `CommandOption` trait (`String`, `i64`, `f64`, `bool`, the `Id<…Marker>` and `Resolved*` / `Mentionable` types, `derive(Choices)` enums). | **OPT-04** NUMBER range | −2^53 … 2^53 (double) **[D]** | [AC §Option type](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-option-type) | Compile-time (literals) | Literal `#[option(min_value, max_value)]` on NUMBER (`f64`) fields, checked as OPT-03. |

| **OPT-06** `min_length` / `max_length` | STRING only; `min_length` 0-6000, `max_length` 1-6000, `min ≤ max` **[D]** | [AC §Option structure](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-option-structure) | Compile-time | `#[option(min_length, max_length)]`, checked by `validate_options` as type-dependent `const _` items over the field's `CommandOption::KIND`. |

| **OPT-08** Choices count | Max **25** choices per option; STRING / INTEGER / NUMBER only **[D]** | [AC §Option structure](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-option-structure) | Compile-time | Choices come from a `derive(Choices)` enum (one variant = one choice, STRING values). `#[derive(SlashCommand)]` checks the field type's `CommandOption::CHOICES.len() ≤ 25` in a `const _` item (`[OPT-08]` E0080); the Choices derive itself allows more variants (modal selects). |
| **OPT-09** Choice name / value length | `name` 1-100 chars; string `value` ≤ 100 chars; value type matches the option type **[D]** | [AC §Choice structure](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-option-choice-structure) | Compile-time (literal) / App-build (localized choice names from the merged locale catalogs; `LocaleSource` overlays never carry reserved keys (Story 11.5)) | `#[choice("Name", value = "v")]` literals measured by `derive(Choices)` with `validate_options` (the same limit as MOD-07 and CV2-09, reported once as OPT-09 with a note). | **OPT-10** Choices exclusive with autocomplete | `autocomplete: true` may not be set when `choices` are present **[D]** | [AC §Option structure](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-option-structure) | Compile-time | A Choices-typed field with `#[option(autocomplete)]` fails in a `const _` item checking `CommandOption::CHOICES` (`[OPT-10]` E0080); so does an `#[autocomplete(field)]` method naming a Choices field. `autocomplete` is a bare flag (maintainer decisions §8); the withdrawn `autocomplete = path` form is a compile error showing the struct form. |
| **OPT-11** Autocomplete types | STRING / INTEGER / NUMBER only **[D]** | [AC §Option structure](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-option-structure) | Compile-time | `#[option(autocomplete)]` on another type is a type-dependent `const _` item over the field's `CommandOption::KIND` (`[OPT-11]` E0080). | **OPT-14** `required` not on subcommands | `required` is invalid on SUB_COMMAND / SUB_COMMAND_GROUP **[D]** | [AC §Option structure](https://discord.com/developers/docs/interactions/application-commands#application-command-object-application-command-option-structure) | Compile-time (by construction) | Subcommands are generated from the pattern; the user cannot set `required` on them. |

## Compile-time strategy

The goal is: if the input is written in the source code, a violation must fail
`cargo check`, not a Publish or a send. The building blocks below make that possible.

### 1. The `custom_id` layout and fixed-length Refs

The layout is normative in the architecture spine (AD-5) and quoted here. Every
character is ASCII (CID-07), so the CID-01 counting unit does not matter.

```text
custom_id = F route ":" [S] [N] body [T]

F      1 char    base62 digit = 16 * generation + flags
                 flags: 1 = S present, 4 = N present, 8 = T present;
                 2 reserved: decodes as CodecError::ReservedFlag
                 v1 writes generation 0 (F < 16); F >= 16 is a CodecError
route  1..24     [a-z0-9._-], unique per App; ids starting with "_" are reserved
S      1 char    Route schema version 1..=61 (`schema = n` on the kind attribute); absent = 0
N      2 chars   per-render select nonce (FR-25); select Routes only
body   inline    field ("," field)*
       by ref    "~" + 11 base62 Ref
T      6 chars   integrity tag: base62 of truncated keyed BLAKE3 over all
                 preceding chars; inline bodies of `signed` Routes only
```

`N` is drawn per send and never equals a nonce of the interaction being answered, nor one
of the run's last eight sends (FR-25): the Responder scans the raw interaction for the
nonces of its Noctis `custom_id`s (the clicked select's `data` and the source message's
selects) and draws outside them and the run's last eight drawn nonces, so a client always
shows the render's declared select defaults. By-Ref ids get a new Ref per send.

| Constant (`noctis-codec`) | Value |
|---|---|
| `FMT_LEN` | 1 |
| `SEP_LEN` | 1 |
| `SCHEMA_LEN` | 1 |
| `NONCE_LEN` | 2 |
| `REF_MARKER_LEN` | 1 |
| `REF_LEN` | 11 |
| `TAG_LEN` | 6 |

A Ref is always exactly **11 base62 characters** (CID-05). 62^11 ≈ 5.2 × 10^19, which
is ≈ 65.5 bits, above the 64-bit entropy floor. Because every part except the inline
body has a fixed width, the worst case is known at compile time:

```text
MAX_LEN = FMT_LEN + route.len() + SEP_LEN + S + N + max(inline, by_ref)
inline  = Payload::MAX_ENCODED_LEN + T
by_ref  = REF_MARKER_LEN + REF_LEN = 12
S, N, T count only when the Route declares them (1, 2, 6), else 0
```

A Route id is at most 24 characters, so a by-ref `custom_id` is at most
1 + 24 + 1 + 1 + 2 + 12 = 41 characters (`MAX_REF_ID_LEN`):
`#[button("setup.step", by_ref, defaults(..))]` and
`overflow = spill` Routes always fit, and the derive still proves it with a const
assertion. A `signed` Route can't be `by_ref` (the Ref is already unguessable).

Decoding is total. A flag set that doesn't match the Route's declared shape, or a
schema that differs from the Route's, is a Stale Payload (FR-60). An unknown Route or
a bad tag is a forged Payload (FR-19). Appending `Option<T>` fields is compatible and
needs no schema bump; every other Payload change bumps `schema`.

### 2. Bounded Payload fields → computable `custom_id` max length

Every type that can appear in a Payload implements `noctis_codec::Field` with an
associated const for its worst-case encoded width, escaping included:

```rust
pub trait Field {
    /// Worst-case encoded width in ASCII chars, or `None` if unbounded.
    const MAX_LEN: Option<usize>;
}
// Widths (base62, ASCII):
// bool                → Some(1)
// u8, i8              → Some(2)   // 255 = "47"; signed values are zig-zag encoded
// u16, i16            → Some(3)   // 62^3  = 238_328 > 65_535
// u32, i32            → Some(6)   // 62^6  > 4_294_967_295
// u64, i64, Id<T>     → Some(11)  // 62^11 > 2^64 − 1
// enum, ≤ 62 variants → Some(1)   // derive(PayloadEnum)
// Option<T>           → T::MAX_LEN + 1 (presence tag)
// BoundedStr<N>       → Some(2 * N)  // ASCII only; worst case after `!` escaping
// String, Vec<T>      → None
```

The kind derives never inspect type names. It sums `<F as Field>::MAX_LEN` plus
`fields − 1` separators through codec `const fn`s and emits a free (non-generic) const
item, which rustc evaluates during `cargo check`:

```rust
#[derive(Button)]
#[button("shop.buy", defaults(style = Primary, label = "Buy"))]
struct BuyButton { item: Id<ItemMarker>, qty: u8 }

// expands (simplified) to:
impl Route for BuyButton {
    const ID: RouteId = RouteId::new("shop.buy");
    const SHAPE: RouteShape = RouteShape::INLINE;
    const SCHEMA: u8 = 0;
    type Payload = Self;
}
impl Payload for BuyButton {
    const MAX_ENCODED_LEN: Option<usize> = ::noctis::__private::codec::sum_fields(&[
        <Id<ItemMarker> as Field>::MAX_LEN,
        <u8 as Field>::MAX_LEN,
    ]); // 11 + 2 + 1 separator = 14
    fn encode_fields(&self, out: &mut FieldWriter<'_>) -> fmt::Result { /* each field, in order */ }
}
impl<'de> PayloadDecode<'de> for BuyButton { /* Self { item: f.field()?, qty: f.field()? } */ }
impl DeclaredRuntime for BuyButton { const RUNTIME: RouteRuntime = RouteRuntime::EMPTY; }
// MAX_LEN = 1 + 8 + 1 + 14 = 24
const _: () = ::noctis::__private::codec::assert_fits::<BuyButton>(); // CID-01
#[cfg(test)] #[test]
fn __noctis_route_width_BuyButton() { /* prints and asserts route_width::<BuyButton>() */ }
// shop.buy: F 1 + route 8 + sep 1 + S 0 + N 0 + body 14 + T 0 = 24 (limit 100)
```

The component kind derives carry it: `#[derive(Button)]` with
`#[button("shop.buy", <codec arguments>, defaults(..))]`, the select kinds
(`StringSelectMenu`, `UserSelectMenu`, `RoleSelectMenu`, `MentionableSelectMenu`,
`ChannelSelectMenu`; every select carries the `N` nonce, so there is no `select`
argument) and `#[derive(Modal)]` (its fields without an input attribute are the
Payload). The codec arguments are `by_ref` or `overflow = spill`, `schema = n` and
`signed`, in any order (`select`, `view` and `opens_modal` are unknown arguments,
CID-03). The runtime arguments AD-6 lists (`ttl`, `one_shot`, `owner`, `permissions`,
`guard`, `rate_limit`) and the handler arguments `response` and `auto_defer` (AD-11)
don't change the length. `ttl = "<duration>"` (`d`/`h`/`m`/`s` groups in that order,
1 s..=365 d) and `one_shot` are accepted on by-Ref Routes only (``[CID-03] `ttl` needs a
by-Ref Route`` otherwise), `response`/`auto_defer` on components and on `#[modal]`
(Story 7.8), and the Route Guards `owner`, `permissions` and `guard` on every kind
attribute (Story 7.7, AD-23 stage 8), and `rate_limit(..)` on every kind attribute
(Story 13.4, checked under INT-14, AD-23 stage 5). The derive validates
the id with
`noctis_rules::cid::validate_route_id` and the argument grammar (unknown or duplicate
arguments, values on flags, `overflow` other than `spill`, `schema` outside 1..=61,
`by_ref` with `overflow = spill` or `signed`) and reports CID-03. If
`MAX_ENCODED_LEN` is `None` (an unbounded field) on an inline Route, or an inline
Route's bound exceeds 100, `assert_fits` panics in const context with a message naming
the rule, the route id and the worst case
(``[CID-01] route `a` can exceed 100 characters: worst case 101``, or
``[CID-01] route `report.reason` has unbounded fields``, each with a `= help:` line).
The mandatory `defaults(..)` block is checked against CV2-08, CV2-09 and MOD-01 (a path
value is a locale key, validated after the Responder resolves it), and `X { .. }.build()` builds the
component; per-render overrides are checked by `noctis_ui::validate` before sending.

A `by_ref` Route needs only `prefix + 12 ≤ 100`, and a `spill` Route's inline form is
used only when it fits. Notes:

- The message is built in const code (a fixed byte buffer turned into a `&str` with
  `core::str::from_utf8`, then `panic!("{}", msg)`), so it carries the route id and the
  computed length. The derive also generates a `#[test] fn __noctis_route_width_<Name>`
  that prints the full width breakdown
  (`cargo test --release -- --nocapture noctis_route_width`).
- The assertion is a free `const _` on a concrete type, so it fires under `cargo check`.
  Generic structs are rejected by the kind derives; a post-monomorphization assertion
  would only fire under `cargo build`.

### 3. Command Pattern expansion and structural validation

`#[command("…")]` of `#[derive(SlashCommand)]` (and `command!`) expands the Command Pattern **inside the proc macro**,
using the semantics FR-8 adopts from tescord, written out here:

1. Groups are `(a|b|…)`; a trailing `?` adds the variant with the group removed.
   Malformed patterns fail with CMD-16.
2. Expansion is left to right in declaration order (FR-8). `expand` collapses whitespace,
   so `#[derive(SlashCommand)]` and App-build first run `validate_pattern_spacing` on the pattern as
   written (words separated by exactly one ASCII space: CMD-02 for an empty word, CMD-01
   for other whitespace); duplicates are rejected, and more than 25 expansions (the default cap,
   `#[command(max_expansions = n)]` changes it) is an error (CMD-15).
3. Each expansion is split into words: 1 word = command, 2 = subcommand,
   3 = group + subcommand; more than 3 is CMD-10.
4. All expansions are inserted into one tree, and the macro checks every node:
   name rules (CMD-01..03, via `noctis-rules`), CMD-11 (a node may not be both a leaf and a group),
   CMD-12 (a base with children may not be a leaf), CMD-13 (≤ 25 children), and the
   size budget CMD-05.

**Example that fails.** The PRD's own example:

```rust
#[command("config (set|get) (prefix|welcome)?", description = "Configure")]
async fn config(ctx: CommandCtx, path: ConfigPath) -> HandlerResult<()> { … }
```

expands to:

```text
config set prefix   → set = GROUP,      prefix = subcommand
config set welcome  → set = GROUP,      welcome = subcommand
config get prefix   → get = GROUP
config get welcome  → get = GROUP
config set          → set = SUBCOMMAND   ✗ already a GROUP
config get          → get = SUBCOMMAND   ✗ already a GROUP
```

`set` becomes both a subcommand (from `config set`) and a subcommand group (from
`config set prefix`). Discord has no way to express that, so the macro emits:

```text
error: [CMD-11] config set: limit a subcommand or a subcommand group, not both, actual `set`
         = note: `config set` makes `set` a subcommand
         = note: `config set prefix` makes `set` a subcommand group
         = help: remove the `?`: "config (set|get) (prefix|welcome)"
 --> src/modules/config.rs:1:11
  |
1 | #[command("config (set|get) (prefix|welcome)?", description = "Configure")]
  |           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

The same error follows for `get`; every violation is reported in one compile. To keep a
bare form, move it to a separate path such as `"config show"`.

The same tree check runs again in `App::build()` on the **merged** trees, because two
patterns that are each valid can collide once Modules are combined (e.g. Module A:
`"config set"`, Module B: `"config set prefix"`). That case is App-build (REG-04).

### 4. Literal string length checks

Wherever a literal is written in an attribute or macro (descriptions, choice names,
labels, placeholders, modal titles, Text Display text), the proc macro measures it.
It counts both Unicode scalar values and UTF-16 code units and compares the larger
against the limit, because the counting unit is not confirmed for several limits
(see [Unconfirmed values](#unconfirmed-values)).

Outside attributes, literals go through small proc macros that measure them at
expansion, so the check fires under `cargo check` (AD-4):

```rust
let label = label!("Configure");          // [CV2-08] if longer than 80
let label = Label::try_from(db_name)?;    // runtime path, same noctis-rules function
```

The public API takes `Label` (not `&str`), so a literal can only enter through the
macro or the checked runtime conversion.

### 5. Static component trees via types and const generics

- **Placement** (CV2-05, MOD-03, WH-02) is encoded with marker traits; an illegal
  child does not implement the parent's child trait, so it is a type error. Each trait
  carries `#[diagnostic::on_unimplemented]` with the rule id.
- **Arity** uses const generics bounded by traits implemented only for the legal
  lengths: `ActionRow::buttons::<N>`, `Section::new([TextDisplay; N], _)`,
  `MediaGallery::new([MediaItem; N])` (CV2-06/07/10). A `const { assert!(…) }` on `N`
  would be post-monomorphization and invisible to `cargo check`, so it is not used.
- **Literal trees: `components!`** (`noctis-macros`, Story 4.4) takes a whole
  literal Components V2 tree and expands it into the typed builder calls above, so
  the placement traits still apply. At expansion it calls `noctis-rules` directly
  (AD-3), which fires under `cargo check`:
  - **Budget:** it counts every node at every depth (CV2-03 against 40) and sums the
    literal `text("…")` nodes with `discord_len` (CV2-04 against 4000). An `{expr}`
    hole counts as one component with no text, and a `..expr` spread as zero; these
    are the tree's static lower bound.
  - **Shape:** Action Row items (CV2-06), Section texts and accessory (CV2-07) and
    gallery items (CV2-10) are counted from the literal children, and literal
    labels, placeholders and descriptions are measured (CV2-08, CV2-09, CV2-11).
  - **Static custom_id uniqueness** (CID-02): it sees every Route component and
    rejects two whose Route type and Payload expression are token-identical and use
    only literal field values, showing both spans.
- **Dynamic parts** (`{expr}` holes, `..expr` spreads, author-built page slices) are checked
  by the runtime validator on the actual tree before sending (FR-24).
- `view!` is a different macro: it builds image Template nodes (AD-15) and has no
  Components V2 rules.

### 6. trybuild compile-fail tests per rule

Every rule marked Compile-time has at least one compile-fail test (a trybuild fixture, or a `compile_fail` doctest for a by-construction rule):

```text
tests/ui/
  cmd/CMD-01_uppercase_name.rs        + .stderr
  cmd/CMD-11_subcommand_and_group.rs  + .stderr   (the `config (set|get) (prefix|welcome)?` case)
  opt/OPT-10_choices_and_autocomplete.rs + .stderr
  cid/CID-01_unbounded_string.rs      + .stderr
  cid/CID-03_uppercase_route_id.rs    + .stderr
  cv2/CV2-05_container_in_container.rs + .stderr
  ...
tests/boundary/
  boundary values: exactly 32-char name, 100-char description, 25 options,
  25 choices, 5 buttons, 40 components, 100-char custom_id
```

- One `trybuild::TestCases::compile_fail("tests/ui/**/*.rs")` test. trybuild runs it
  with `cargo check`. There is no trybuild `pass` suite: boundary passes are ordinary
  integration tests in `tests/boundary/`, compiled by `cargo test --release`.
- For a rule Noctis diagnoses, the `.stderr` must contain the rule ID, so the mapping
  from error to this catalog is tested too. For a `Compile-time (by construction)`
  rule, the fixture's source (or a `compile_fail` doctest) carries `// [<RULE-ID>]` on
  the offending line instead, and the `.stderr` is rustc's own error.
- Fixtures that need a facade feature live in `tests/ui-<feature>/` and run, and are
  blessed, in the CI run of exactly that feature (`cargo hack --each-feature`).
- `.stderr` output varies across rustc versions, so the UI tests run on the toolchain
  pinned in `rust-toolchain.toml` (stable 1.97.0), locally and in CI; a toolchain bump
  re-blesses them in the same PR (AD-28).
- App-build rules get unit tests asserting the exact `BuildError` variant; Runtime
  rules get unit and property tests (and Testing kit cases, FR-51) asserting the typed
  error is returned **before** any HTTP request.
- A CI check (`cargo run --release -p xtask -- rules-catalog`) compares the rule IDs
  in this file against the IDs found in tests, fixtures and doctests, and fails when a
  Compile-time, App-build or Runtime rule has no test of the kind its tier requires.
  Rows whose Enforcement column is a parenthesis only (permitted, out of scope, no API
  in v1) are documentation-only; a row that says `see <ID>` or `as <ID>` (LOC-05,
  MOD-08) is covered by that rule's tests, and an alias row needs no test of its own.
- How the check reads the Enforcement column: tiers are split at ` / ` outside
  parentheses and code. A `Compile-time` tier is by construction when the text in its
  parentheses before the first `;` says "by construction" (so INT-05's
  "`#[command]`/`#[handler]` check; typestate by construction" is diagnosed);
  otherwise Noctis diagnoses it. Every `App-build`, `Runtime` or `Startup` tier needs
  a unit test, including `Runtime (by construction)` (LOC-06, INT-12, MSG-08, ATT-04).
- Fixtures are named `tests/ui/<area>/<RULE-ID>_<slug>.rs` (or under
  `tests/ui-<feature>/`), `<area>` being the id's area lowercased (`CV2-05` lives in
  `cv2/`) and `<slug>` lowercase words joined by `_`, with the `.stderr` beside them.
- A unit test cites a rule when its `#[test]` (or `#[tokio::test]`) function name
  contains the id's snake token: `cv2_03` in `fn cv2_03_forty_one_fails()`.
- A requirement whose test lands in a later story is listed in
  `xtask/rules-pending.toml` with the story that adds it. An entry whose test already
  exists fails the check, so the list only shrinks; it is empty by Story 14.4, except entries for Epic 15 stories.
